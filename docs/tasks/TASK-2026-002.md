## Implementation Notes：实际接口与风险

1. `db29_combat_timeline.gd::step_movement/step`先完成瞄准／移动采样，然后`fire.advance_fixed`产生并扣除整步合法发射，再`projectiles.step`推进弹丸。`networking/network_manager.gd`约464行调用该链，在约471行进入combat后才分类并广播终止。现阶段没有活动伤害消费者。不得在这一后置位置简单批量扣血来声称符合步内伤亡规则。
2. `fixed_fire_scheduler.gd::step/_emit`用发射时间和weapon.instance_id排序，实际发射前重验资格，但尚未收到更早命中的状态更新。`db29_projectile_simulation.gd::step`按存储推进碰撞后排序实际输出，不在事件间结算并更新世界；`ProjectileUnitMotion`既有采样与拓扑校验不能直接承担步内死亡后候选更新。单纯排序末尾数组无法撤销已经扣弹／采样的非法晚发射，也不应撤销合法早发射。
3. **工程提案**：在共享30Hz协调器内分离“下一候选”和“提交”；只比较实际发射／终止候选，在最早时刻提交、让服务器结算消费者完成状态变更，再使受影响武器及碰撞候选失效并重验。运行计时／库存仍以RuntimeWeaponInstance为唯一权威；不先全步扣弹再回滚、不排序全部活弹丸、不重算全阵营。不改冻结legacy的60Hz阶段契约。跨类型同刻稳定编号映射及失败／部分提交处理尚须形成可核验契约，未选择具体算法。
4. 终止事件含内部projectile_id、source_event_id、emission_order、slot_generation、时间、位置、速度、累计距离和命中信息。槽回收前构造值事件，随后清空source/ammo/ignore；终止值本身**不带Ammo Resource**。不能到消费时再读已回收槽，也不能依赖源单位仍在场查弹药。建议在回收前保留只供服务器消费的不可变结算输入（弹药值或有明确生命周期的缓存），记录规则／DATA身份；具体持有／释放与去重容量待实现契约核对。
5. 去重应绑定对局及发射生命周期，不能只用slot_generation（各槽会有相同代次）、目标ID或source单位ID。候选使用对局身份＋全局emission_order并交叉核验source_event_id/projectile_id/generation；若进入独立效果结算，再区分成员生命、班组压制、车辆等接收域。消费成功后才能确认已结算；重复相同值无第二副作用，冲突重复须诊断。清理策略不能任意淘汰仍可合法重投的身份。此为工程候选，未新增协议或持久化格式。
6. `UnitState.health`总生命setter会按数组重分配成员生命，仅兼容旧setup。`apply_prototype_damage`扣首名存活成员且不溢出，为旧适配，并非已确认选择算法。`SoldierState.health`可操作单名成员，在生死转换同步触发`living_changed`；`SquadWeaponChannels::_living_changed`移除死亡携弹并重算受影响岗位／库存。未来单成员受伤入口必须服务器校验稳定unit/member身份、伤害有限且合法、存活资格，单成员截断到0并不溢出；存活残血不触发减员或额外效率惩罚。总HP派生，固定N不变，接替沿现有事件链，不能重复扣阵亡弹药。
7. 共享受击体不提供被击中成员身份。§25明确成员选择待细化；不得直接采用首存活、均匀随机、最近点或第三方死亡排序字段。若未来决定随机，需同时确认服务器随机／实际结果记录策略；本轮不抽样、不写入v1 random_result扩展。
